# PatientProbe — Architecture and Design Decisions

## System Architecture

PatientProbe is an automated patient simulator built with Python and LiveKit Agents. It initiates outbound telephone calls to a fixed assessment number, interacts with an AI receptionist using realistic patient scenarios, and captures conversations for behavioral evaluation.

The system uses LiveKit Agents in **pipeline mode**, with independent speech-to-text (STT), language model (LLM), and text-to-speech (TTS) components. Deepgram Nova-3 transcribes incoming receptionist audio, OpenAI GPT-4o generates patient responses based on scenario-specific instructions and conversation history, and Deepgram Aura-2 Thalia synthesizes spoken responses. Silero VAD supports speech activity detection, while LiveKit manages audio streaming, turn handling, and the agent session. This separation was intentional: each component can be configured or replaced independently, making the system easier to debug and tune than a tightly coupled speech-to-speech architecture.

Call orchestration is separated from conversational behavior. `make_call.py` validates the selected scenario, creates a LiveKit room, and dispatches the worker with scenario metadata. `agent.py` initializes the voice session, establishes the outbound SIP connection, handles conversation events, and writes speaker-labeled transcripts. `scenarios.py` defines patient identities, objectives, behavioral instructions, and any dependencies on earlier appointments. The session starts listening before the outbound call is placed to reduce the risk of missing the receptionist's initial greeting. The assessment destination is hardcoded to prevent accidental calls to other numbers.

## Engineering Decisions and Tradeoffs

**Speech pipeline and provider selection.** Deepgram was selected for both STT and TTS primarily because available API credits reduced experimentation costs, and using one provider for both speech stages simplified integration. Nova-3 and Aura-2 provided a practical starting point for a working conversational system without spending disproportionate time comparing providers. GPT-4o was used for contextual reasoning and scenario-driven responses. The modular pipeline also made it possible to focus debugging on individual stages—speech recognition, response generation, speech synthesis, or turn handling—rather than treating every conversational failure as a single opaque problem.

**Telephony and outbound connectivity.** Establishing reliable outbound SIP calling was the largest implementation challenge. Twilio and Telnyx were both evaluated as telephony options, including their trial limitations, outbound calling capabilities, and integration requirements. The final approach uses LiveKit's SIP participant API with a configured outbound trunk, keeping telephony initiation within the same framework that manages the agent session. The launcher creates a room and dispatches a scenario, while the worker establishes the telephone connection. This avoids embedding telephony setup inside the scenario definitions and keeps the call lifecycle easier to reason about. Ringing timeouts, maximum call duration, and failure handling provide safeguards against unanswered or stalled calls.

**Turn-taking and conversational quality.** A realistic patient simulator must do more than ask a predetermined sequence of questions. Scenarios therefore define goals and patient context while allowing GPT-4o to respond to the receptionist's actual behavior. Silero VAD and LiveKit turn-handling settings support conversational pacing and endpoint detection. During testing, awkward pauses, interruptions, and premature endings showed why voice-agent evaluation cannot rely on transcript correctness alone. We iterated on scenario instructions and conversation-ending behavior, while recognizing that prompt changes alone cannot guarantee correct timing or call termination. The system also uses call-lifecycle safeguards and activity monitoring to manage calls that stall or exceed their configured duration.

**Testing environment and state.** Beyond SIP connectivity, working within the assessment's test environment introduced additional challenges. The receptionist could create demo patient profiles, maintain appointment state across calls, and route transfer requests through the available test infrastructure. Consequently, scenarios involving rescheduling or cancellation require appointment details confirmed in an earlier conversation rather than invented booking state. The launcher validates these dependencies and requests confirmation before proceeding. This reduces false findings caused by inconsistent test setup and helps distinguish receptionist behavior from limitations of the testing environment.

**Recording and observability.** LiveKit session recording is enabled during calls, while the application independently writes speaker-labeled transcripts in human-readable TXT and structured JSONL formats, along with run metadata. Audio was exported from LiveKit Cloud after testing, converted to MP3, and matched to the corresponding run directories using timestamps. Automatic audio downloading is not implemented. Retaining recordings, transcripts, and metadata together makes findings traceable to specific conversations and timestamps. Multiple attempts are preserved, including incomplete calls, so the evidence reflects actual testing rather than only successful examples.

## Limitations and Lessons Learned

The system depends on external speech, language-model, LiveKit, and telephony services, so end-to-end responsiveness is affected by network and provider latency. The chosen pipeline favors modularity and straightforward debugging over minimizing every possible processing step. The current implementation does not include a benchmark comparing alternative STT, LLM, or TTS providers, and its latency improvements were assessed through conversational testing rather than formal performance measurements.

The most important lesson was that **a technically connected call is not necessarily a successful voice interaction**. Natural pacing, coherent follow-up questions, accurate handling of corrections, and a sensible ending all affect the quality of the test. PatientProbe therefore evaluates conversations using both recorded audio and transcripts, while keeping the simulator's own limitations separate from potential issues in the receptionist being tested.
